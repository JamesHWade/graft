# Graft v0.1 behavior requirements

Status: Phase 0 characterization baseline

This document identifies the package behaviors that must survive the v0.1
redesign. It is a test-porting guide, not a requirement to preserve current
function names, object classes, database tables, or SQL.

The governing architecture is `design/v0.1-redesign.md`. When a current test
conflicts with that decision, preserve the user-visible semantic guarantee and
replace the representation-specific assertion.

## Classification rule

A behavior is durable when a package user, host application, or auditor can
observe it without knowing Graft's internal table layout. A test is legacy when
it requires a particular S3 structure, exported `kg_*` function, physical
current table, generated relation row, SQL view, or migration operation.

Tests may contain both kinds of assertions. Port the durable assertion and
delete or rewrite the legacy assertion. The current test count is not an
acceptance criterion.

## Durable semantic requirements

### Contract and store lifecycle

- **BR-01 Contract integrity:** Graft loads a compiled contract from a supported
  provider only when its content and digests are internally consistent. A
  data-dict YAML build records source-spec and resolved export-format versions
  separately, snapshots the source bytes once for preflight, CLI export, and
  source/build fingerprints, and fails if the selected CLI changes during
  export or version discovery. Its public manifest strips all column examples
  and ranges, dataset and table origins, and table source locators while the raw
  input still binds the source and build digests. Retained contract metadata is
  public and may contain observed or sensitive values embedded manually.
- **BR-02 Runtime independence:** A committed manifest and an existing store can
  be reopened and used without a LinkML compiler, the data-dict CLI, or any
  source-contract toolchain.
- **BR-03 Store identity:** Operations bind to one store format, store identity,
  and active schema digest. Unsupported or mismatched stores fail explicitly.
- **BR-04 Ownership and capability:** Closed and read-only stores reject writes;
  Graft closes only connections that it owns.
- **BR-05 Safe initialization:** Initializing a store is idempotent, and failed
  initialization leaves no partially usable store.

### Planning and validation

- **BR-06 Read-only planning:** Planning performs no persistent write and
  reports candidate changes before acceptance.
- **BR-07 Record validation:** Required fields, types, enums, bounds, temporal
  rules, cardinality, identifier formats, and semantic invariants that exist in
  the compiled contract are checked against that contract. Preserved provider
  metadata is not silently treated as an acceptance rule. The data-dict table
  profile rejects scalar and list `number(id)` types. A lexical guard rejects
  every token whose magnitude exceeds `2^53 - 1` and any lexically nonzero
  token that would overflow to non-finite or underflow to zero in R. Its
  omitted-zone datetimes require RFC 3339 offsets,
  `time_zone: UTC` datetimes require zoneless input interpreted as UTC, and
  both forms enforce a six-digit fractional-second limit.
- **BR-08 Reference validation:** Object references resolve against records in
  the same candidate set or accepted store and respect allowed target classes.
  A data-dict scalar foreign key participates in this validation but does not
  create a graph traversal edge. An optional scalar foreign key normalizes an
  empty or whitespace-only string to missing before validation, and a primary
  `id` cannot also be a foreign key because record IDs are globally unique.
- **BR-09 Batch consistency:** Duplicate record IDs, origins, identifiers, and
  relation values are rejected deterministically with source-row context.
  Record IDs are globally unique across classes and tables.
- **BR-10 Review integrity:** A commit plan is bound to its canonical records,
  provenance, schema, store, and expected heads. Tampered, stale, or cross-store
  plans fail before mutation.

### Identity and provenance

- **BR-11 Stable identity:** Exact identifiers and producer origin keys resolve
  the same real-world record to one stable Graft ID across batches.
- **BR-12 Deterministic normalization:** Declared identifier normalization, such
  as canonical URL and DOI handling, is stable and versioned by the contract.
- **BR-13 Conflict safety:** Conflicting exact identifiers or incompatible
  internal IDs fail without changing accepted identity state.
- **BR-14 Traceable acceptance:** Every observation records the producer, source
  run, idempotency identity, accepted record, and applicable schema.

### Atomic commits and revisions

- **BR-15 Atomic acceptance:** A multi-class commit accepts all valid records and
  metadata in one transaction or accepts none of them.
- **BR-16 Explicit dispositions:** Each observation is classified as insert,
  update, or match. Inserts and updates create revisions; matches point to the
  existing revision.
- **BR-17 Idempotent replay:** Repeating a committed producer and idempotency key
  returns the original logical result without new revisions or observations.
- **BR-18 Immutable history:** Accepted revisions are append-only, ordered
  deterministically, linked to their predecessor, and bound to their exact
  schema and batch.
- **BR-19 Canonical content:** Equivalent logical values produce the same content
  digest. Ordered collections retain order; unordered collections canonicalize
  independently of input order.
- **BR-20 Failure rollback:** Validation, identity, revision, or projection
  failures before commit leave no partial authoritative state.

### Retrieval, history, and evidence

- **BR-21 Current retrieval:** Users can retrieve current accepted records and
  contract-projected relationships without seeing internal metadata or
  sensitive payload fields that the contract withholds. Record IDs remain
  public operational keys.
- **BR-22 Historical retrieval:** Users can hydrate the accepted state at a
  deterministic commit boundary using the historical schema and sensitivity
  rules.
- **BR-23 Bounded results:** Record, search, history, claim, evidence, and graph
  queries require enforceable bounds, report truncation, and order results
  deterministically.
- **BR-24 Graph meaning:** Object relations emitted into the compiled graph
  contract, semantic statements, provenance, supersession, and evidence links
  produce the same logical nodes and edges regardless of their physical
  projection. Provider metadata that was not mapped to graph semantics does
  not acquire traversal meaning implicitly.
- **BR-25 Evidence precision:** Claims retain exact supporting or challenging
  sources and locators across ingestion and historical retrieval.
- **BR-26 Integrity diagnosis:** Graft detects broken revision chains, missing
  schema or identity references, and stale derived projections without treating
  a projection as an independent source of record content.

### Open knowledge and agent access

- **BR-27 Explicit synchronization:** Database acceptance and OKF filesystem
  synchronization are separate, observable operations. A filesystem failure
  does not misreport the database transaction.
- **BR-28 Proposal-only edits:** Editing OKF proposes a change. Accepted knowledge
  changes only through the ordinary reviewed commit contract.
- **BR-29 Working-tree safety:** OKF status distinguishes current, modified, and
  stale state; rejected deletions, symbolic links, unrelated bundle metadata,
  and post-review edits cannot bypass review.
- **BR-30 Progressive disclosure:** OKF context and agent tools expose bounded,
  schema-aware accepted knowledge and remain read-only.

## Representation-specific legacy assertions

The following are not v0.1 compatibility requirements:

- **LR-01 Physical current tables:** Exact manifest table names, column order,
  foreign keys, indexes, and row counts in class-specific tables.
- **LR-02 Generated relation storage:** Exact relation-table schemas, synthetic
  relation IDs, retained physical rows, and delete-then-append behavior.
- **LR-03 Generated graph SQL:** Exact graph-view names, SQL text, column layout,
  and the requirement that graph accessors return a lazy table.
- **LR-04 Dual-state drift:** Tests that mutate typed current tables and compare
  them with revision heads. Replace them with revision-chain and projection
  freshness or rebuild tests.
- **LR-05 Physical migrations:** DDL operation lists, additive table or column
  migration, relation-table creation, graph-view rebuilding during migration,
  and old migration-plan classes.
- **LR-06 Current API shape:** `kg_*` names, unused mode or validation arguments,
  exact S3 constructors, list layouts, print output, and snapshots that assert
  only legacy wording.
- **LR-07 Internal write choreography:** Exact counts or ordering of DBI calls,
  direct inspection of private metadata tables, and implementation-specific
  failure injection points. Retain only the atomicity they demonstrate.
- **LR-08 Bundled applications:** Package paths and host mechanics for Continuous
  Intelligence, Materials Market Radar, Coworker, and Tempest-specific adapters.
  These tests move with the applications rather than constrain core Graft.

Classed error families, machine-readable context, and absence of partial writes
are durable. Exact prose is durable only when it is intentionally documented as
part of the public interface.

## Current test disposition

| Current area | Disposition for v0.1 |
|---|---|
| `test-schema-*` and `test-store-init.R` | Retain contract integrity, lifecycle, ownership, reopen, and mismatch behaviors; rewrite table-catalog assertions. |
| `test-validation.R` | Retain semantic validation and source-row context through `graft_plan()`. |
| `test-identity.R` | Retain exact reconciliation, normalization, conflicts, promotion, and deterministic IDs; implement lookup in bulk. |
| `test-ingest.R` | Retain atomicity, dispositions, replay, origin updates, rollback, and reopen behavior through plan/commit; replace physical relation and dual-state assertions. |
| `test-history.R` | Retain bounded history, point-in-time types, canonical values, sensitivity, and schema integrity; rewrite current-table drift checks. |
| `test-records.R`, `test-search.R`, and claim tests | Retain logical results, filtering, sensitivity, ordering, bounds, and truncation; rewrite names and return-shape assumptions. |
| `test-graph.R` | Retain logical edges, direction, predicates, hops, bounds, and dangling-reference errors; remove exact generated-view and laziness requirements. |
| `test-okf*.R` | Retain explicit sync, status, stable snapshots, context, reviewed edits, and tamper rejection; route acceptance through the shared plan. |
| `test-agent-tools.R` | Retain read-only bounded semantics; regenerate the tool surface from the new retrieval API. |
| `test-migration.R` and physical schema-diff tests | Remove physical migration expectations; add semantic schema registration, compatibility validation, and projection rebuild coverage. |
| Application and Tempest adapter tests | Relocate with their host examples; do not port into core Graft. |

## Porting procedure

For each current test file:

1. Label each expectation with the relevant `BR-*` or `LR-*` requirement during
   the implementation review.
2. Write a black-box v0.1 test for every referenced `BR-*` behavior before
   deleting the legacy path.
3. Delete `LR-*` assertions once no durable behavior depends on them.
4. Prefer public operations and logical results. Use internal inspection only
   to prove append-only history, rollback, or projection rebuildability.
5. Record any newly discovered user-visible guarantee here before treating it
   as required compatibility.

## Phase 0 exit criteria

- Every current behavior area has a retain, rewrite, remove, or relocate
  disposition.
- The benchmark in `bench/ingest-baseline.R` records comparable 100- and
  1,000-record elapsed times before implementation begins and after set-based
  ingestion lands.
- Future implementation reviews can trace each retained test to a `BR-*`
  requirement rather than to the old representation.
